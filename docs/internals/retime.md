# Internals of `stage apply retime_speed` and `stage apply retime_longer`

How the code of these stages is built, how a render reaches its kernels, how it is checked and what limits it has. They render the two registered styles of `S_Retime`. The user reference is the `S_Retime` section of [Effects](../effects.md); its parameters are described in [Driving the effect parameters](../parameters-guide.md) and its stages in [Effects provider](../stages.md#effects-provider). The architecture every effect shares is in [Effect internals](README.md). The frame route that serves the clip frames is shared with `time_warp_rgb_autogen` ([`S_TimeWarpRGB` internals](time-warp-rgb.md)).

## What it computes

Each output frame is made from the clip frames around a source time. Retime_Speed maps output time t to source time `speed` x t, and Retime_Longer maps it to t x 100 / (100 + `percent_longer`) (INFERRED from the program constructors). For the two frames around the source time the program builds a luma plane of each (`monochrome`) and an image pyramid (`make_mipmap`), estimates the optical flow between them on the pyramid (`optical_flow`: three planes, flow u, flow v and a confidence), turns the flow into four interpolation maps (`optical_flow_interp_maps`), warps the frames along them (`warp_rel`) and, where the source time falls between two frames, dissolves the two warped frames into each other (`dissolve`); `element_of` picks single planes out of multi-plane results. These are the nodes of the compiled plans (MEASURED with the device report below); what each node computes is read from the code (INFERRED).

Source time and requested frames (INFERRED from the constructors in `crates/effects/fx_eval/src/programs_native.rs`): the source frame is `start_frame` plus the output frame number times the speed (`defun_retime_source_frame`, line 5611), and Retime_Longer sets the speed to 100 / (`percent_longer` + 100) (`eff_retime_longer`, line 5331). On a progressive host the program asks for the source frame rounded to a whole frame and the frame after it, and the fraction left over is the `dissolve` amount (`defun_retime_fields`, line 5540). The frame route clamps every request to the clip: `checkout_request` (`crates/effects/fx_exec/src/twframe.rs:77`) takes the smaller of the requested frame and the last clip frame, computed from N, the clip length of `--tw-route`, and the larger of that and the lower limit, which is 0 on the stages. A source time past the last frame therefore reads the last frame: the worked render of 3 frames with `speed` 2.5 exits 0 (MEASURED below), and `FRAME-REQUEST-OUTSIDE-CLIP` is not reached through the stages' route (INFERRED).

The flow op (INFERRED from the crate headers and `defun_retime_core`, `programs_native.rs:5459`): `optical_flow_entry` builds the parameter block and runs the pyramid body and the solve body in a fixed order; `optical_flow` and `optical_flow_pyramid` build the image pyramid of the two luma planes and its level table (level sides from `flow_level_dims`, `crates/effects/kernels/optical_flow_entry/src/placement.rs:43`); `optical_flow_resample` resamples between levels (a cubic B-spline when scaling down, Catmull-Rom when scaling up); `optical_flow_solve` walks the levels and runs nested warp, outer and inner iterations in which `fma_mix` forms the coefficients, `flow_update` takes a 2x2 normal-equation step per pixel with a clamp, the relaxation (`relax.rs`) smooths the update, `diff_sum` measures the change, the 3x3 median (`median.rs`) filters the flow and the polar step (`fetch.rs`, `polar`) forms per-pixel weights with the vector power and exponential lanes of `vmath.rs`. The op returns flow u, flow v and a confidence plane. The program passes fixed iteration counts and a fixed smoothing deviation, the smoothness weight lambda (`smoothness` through `TO_LAMBDA`), a median flag and a texture scale proportional to `std_texture`. `flow_scale` only scales the flow view of the Result answers that stay refused, and `motion_blur`, which the stages do not offer, adds a `blur_warp` pass along the flow when it is above 0. `optical_flow_interp_maps` splats the flow forward, keeps per target pixel the candidate with the smallest matching error, fills the holes by repeated 3x3 means up to a fixed pass count and interpolates the four maps that `warp_rel` reads (`crates/effects/kernels/optical_flow_interp_maps/src/lib.rs`, `crates/effects/fx_exec/src/device_ops_interp_maps.rs`).

## Render flow

1. `sapphire stage apply retime_speed|retime_longer --width W --height H --depth D [--fps N[/D]] [--frames N] [--param ID=V]` checks the parameter against the list `stage list --json` prints and refuses a keyed value, an unknown id, a value outside its range, a stage id of a style that is not rebuilt and a width below 2 with exit 3 before any frame is read.
2. The stage reads the whole clip into memory, each frame converted to 'ae32' words (`crates/neutral-handoff/src/fxstage.rs:1673`). With `--frames` the clip length must equal it (exit 4 otherwise). The clip is held as 16 bytes a pixel: 33,177,600 bytes a 1920x1080 frame, about 8.0 GB for 240 frames; there is no streaming mode and no limit, and an allocation the system refuses ends the process (INFERRED from the code; the same read in `time_warp_rgb_autogen` is MEASURED in [`S_TimeWarpRGB` internals](time-warp-rgb.md)).
3. For each output frame f the stage builds the runner arguments: the program, `--size`, `--geom` and the frame index (`--host-frame`, `--ctx-time`), the options of the `host` column, the placement entry (empty at 50x7 and 64x32), the `fixed` column `--tw-route N,0,1,1,0,0,1` with N the clip length, the host values of the frame (`get_percent_time` is f / (N - 1), so a one-frame clip gives a value that is not finite and is refused) and `--ns-default-unbound`. The stage passes no `--flow-host-phase`, so every stage render runs the host buffer phase 0. The seven `--tw-route` fields (`crates/effects/fx_exec/src/fxrun.rs:597`, `TwRoute` in `crates/effects/fx_exec/src/twframe.rs:261`) are the clip duration in frames (the upper clamp above), the lower limit cell (the lower clamp is this cell divided by the step), the local time step (the host call argument is trunc(step x stored time)), the host id and a step flag (for one host id with the flag set the step doubles), and two frame-range selectors: the first rounds the frame range up, and the second, when 0, selects the lane path, which is refused (INFERRED from `twframe.rs`). Frame numbers count from the first frame of the clip, so a clip that starts at another host frame changes no field (INFERRED); an interlaced host is outside the stages (see step 4).
4. `fx_exec` builds the program from the native constructors and compiles the plan. The source time and the frames it needs come from the program; with the field query answering field order 0 no plan requests an interlaced field.
5. Each `get_frame` node asks the frame route for its request (frame and stored time, `crates/effects/fx_exec/src/twframe.rs:269`) and logs it. A request that has not been served ends the run with `get_frame request frame K stored S`; the stage reads the request, checks it (inside the clip, stored time equal to the frame, at most 8 distinct frames), adds clip frame K as an in-memory `--frame-words K,K` entry and runs the frame again, until every request is served (`crates/neutral-handoff/src/fxstage.rs:1162`).
6. The kernels run node by node (the order INFERRED from the constructors): `monochrome` and `make_mipmap` on the requested frames, `optical_flow` on the pair (pyramid build, the iterated solve per level, smoothing and the final warp, with the plane placement taken from `flow_host_phase`), `optical_flow_interp_maps`, `warp_rel` on each frame and `dissolve` where the source time falls between two frames. The output does not depend on `SAPPHIRE_THREADS` or `SAPPHIRE_PAR_MIN` (equal at threads 1, 3 and 12, MEASURED in the `S_Retime` section of [Effects](../effects.md), and the `t` golden rows): the tile kernels of `optical_flow_interp_maps` run on one chunk that covers every row at any thread count.
7. With a device, each node runs on the device when its op passed the self-check there ([Device path](#device-path)); otherwise, or for a declined shape, on the CPU with the same bytes.
8. The output words are relaid to the frames/2 planes and written: one output frame per input frame. Retime_Longer therefore writes N frames that cover the first N x 100 / (100 + `percent_longer`) source frames; no stage option writes more frames than it reads, and no page of the repository describes how to obtain the longer clip in a pipeline (open item). INFERRED: an input padded at its end to N x (100 + `percent_longer`) / 100 frames, for example by repeating its last frame, gives the longer clip, because its output frames then map to source frames inside the original clip.

`fx_run Retime_Speed` and `fx_run Retime_Longer` run the same plans when given the same options; the stage builds them in `crates/neutral-handoff/src/fxstage.rs`, and the frame request loop of step 5 is the stage's. `fx_run` alone also takes `--flow-host-phase N`, the host buffer phase described under [Verified scope and limits](#verified-scope-and-limits).

## How parity is judged

An effect counts as rebuilt when every registered style passes seven checks on the final binary: program text, builtin classes, data read, literals, compiled plan, combination tables and execution ([What rebuilt means](../effects.md#what-rebuilt-means)).

- 37 verified comparisons, 46 recorded renders and 46 re-rendered units (`docs/data/effects_status.tsv`, line 14, and the status table of [Effects](../effects.md)). The 37 counted comparisons (20 of Retime_Speed and 17 of Retime_Longer; 17 at 50x7, 16 at 64x32 and 4 at 72x24) are byte identical to the original's output by full SHA-256. The other 9 recorded renders, at 64x32 on the optical flow route, are controls and are not counted: they differed under the expected outputs recorded before the native code took the host buffer phase as a host value, and equal the original's output since (information only).
- Every re-rendered unit is byte identical to its recorded render: the 42 at 50x7 and 64x32 through `fx_run` and through the two stages, and the 4 at 72x24 through `fx_run` with their recorded host buffer phase.
- Through the stages: 33 of 37 counted comparisons (Retime_Speed 18 of 20, Retime_Longer 15 of 17) use the stages' host arrangement and are byte identical through `sapphire stage apply` (README "Effects and stages" table; [Effects provider](../stages.md#effects-provider)). The 4 at 72x24 were recorded at host buffer phases the stages do not run and are rendered through `fx_run`.
- The `optical_flow` op was also compared word for word with the original on 208 cases (182,964 output floats): every word of the 205 cases that render is equal, NaN against NaN words aside, and on the other 3 the native code stops where the original stops (MEASURED). The 24 recorded renders of the original's own style records (15 of Retime_Speed, 9 of Retime_Longer) are equal through `fx_run` and through the stages.
- No comparison of the counted set differs from the original.

## What needs the comparison harness

The comparison with the original runs in an emulator harness kept outside this repository: the 37 counted comparisons, the 208 word-for-word cases of `optical_flow`, the recorded renders of all 46 units and the recorded host buffer phases of the 72x24 renders are not in it. A render at a phase other than 0, such as the 72x24 renders of Retime_Longer, needs the full `fx_run` argument list the stage builds plus `--flow-host-phase N` and the served frames, which the repository runs only inside the stage. Without `VEC_DIR`, `crates/neutral-handoff/tests/fx_stage_parity.rs` and the stored-data tests of `fx_eval` and `fx_exec` print `NOT RUN` and pass. The full report, with the runs behind each figure, is identified by its SHA-256 in [Evidence](../effects.md#evidence). The same holds for three questions the repository cannot answer: how far a processor whose reciprocal square root estimate differs from the exact value moves the output (the repository states only that one ulp in it changes the output), on which inputs the NaN difference of the median plane reaches the output, and at which host buffer phases the original's flow becomes a constant map at a given size.

## Verified scope and limits

- Verified: 50x7, 64x32 and 72x24, Retime_Speed and Retime_Longer, on a clip of 240 frames at a whole frame rate from a progressive host, with the clip frames served by request, at depth 32; `speed` and `percent_longer` at the values listed in the `S_Retime` section of [Driving the effect parameters](../parameters-guide.md), taken on the 16.16 grid of a host slider. Other sizes, values, frame rates and clip lengths run the same code and are INFERRED. A rate such as 30000/1001 renders (exit 0, MEASURED); its output is INFERRED.
- Host buffer phase. The optical flow op sums the rows of its pyramid planes with an eight-lane vector loop when a row holds 64 or more elements; the order of that sum, and so the last bits of the result, depends on where the row starts relative to a 32-byte boundary, which is set by the host's memory allocator. The original's own output therefore depends on the address phase of its buffers, and at some phases the flow becomes a constant map. On rows of 1,200 or more elements the relaxation and the flow-build stencil also split each row by bit 5 of its address (the phase modulo 64). The native code takes this as a host value: `flow_host_phase` (`KParams`, `crates/effects/fx_exec/src/types.rs:289`) is the address phase in bytes, modulo 64, of the first level-0 image of the op; every other plane of the op is placed from it by the in-op chain, arithmetic on the plane sizes (`crates/effects/kernels/optical_flow_entry/src/placement.rs`). Valid values are the multiples of 4 from 0 to 60; any other is refused with `OPTICAL-FLOW-BAD-HOST-VALUE-REFUSED`.
- The default 0 equals, in its low 5 bits, the first level-0 phase the reference host gave both styles at 64x32 and Retime_Speed at 72x24 and 128x64 (MEASURED). The stages always run 0. `fx_run --flow-host-phase N` is needed only to reproduce a render whose host placed that image at another phase, as for the recorded Retime_Longer renders at 72x24 (16 modulo 32); no counted size reads bit 5, because the bit 5 splits apply only on rows of 1,200 or more elements. From each render's own first level-0 phase, the in-op chain predicts every recorded plane address phase at the counted sizes (MEASURED). Rows of 907 samples or more in the solve's residual and of 1,200 or more in its relaxation, derivative, polar and stencil steps take a summation order from plane phases that no render recorded at those widths (INFERRED). `xy_to_polar` keys its own magnitude plane phase (`polar_mag_phase`, default 0) on 1,200 pixels or more; it is reached only by the Result answers that stay refused. In a host application the phases come from that host's allocator, which the plugin does not contain ([limits common to the effects](../effects.md#limits-common-to-the-effects)).
- A 1920x1080 render through the stages runs phase 0 on rows of 1,920 elements, so every phase-dependent loop above, the bit 5 splits included, takes its order from that phase; no recorded render checks a width of 1,200 or more, so its equality with a host is INFERRED, and which phases give a constant flow in the native code or in the original at that size is not measured (open item).
- The 4 counted renders at 72x24 differ from the stages' host arrangement only in the host buffer phase (the `S_Retime` section of [Effects](../effects.md): the stages run the arrangement of the recorded renders except the host buffer phase).
- NaN: on inputs that hold NaN, outputs are compared as NaN values (finite words and NaN positions equal; payload and sign bits not verified). A NaN from two NaN operands follows the x86 first-operand rule, which the recorded renders do not confirm; 45 of the 208 word-for-word cases hold such words. Values inside `optical_flow` are not claimed on NaN input: its median plane holds NaN where the original's does not, and every output word still equals the original's on the one compared case (MEASURED).
- Approximate instruction: the flow solve runs one reciprocal square root estimate. The emulator computes it exactly and a change of one ulp in it changes the output (MEASURED by a unit test and a mutant), so on a processor whose estimate differs the output can differ (INFERRED). The pyramid build and the resample run no approximate instruction.
- `ROUTE AVX2-ONLY`: the optical flow ops are rebuilt on the original's AVX2 and FMA route; the SSE and AVX routes are not rebuilt.
- Not rebuilt: the styles Retime_Scale, Retime_FPS, Retime_Length and Retime_Variable_Speed, the Result answers other than the first, the host image handle route of the flow op, interlaced fields and keyed parameter values. Depths 8 and 16 go through a conversion that is not verified.

## Device path

| op | device kernel | NaN exact | on the counted plans |
|---|---|---|---|
| `optical_flow` | `OPTICAL_FLOW`, `crates/effects/fx_exec/src/device_ops_flow.rs` | yes (`NAN_EXACT_WRITTEN`) | yes |
| `optical_flow_interp_maps` | `INTERP_MAPS`, `crates/effects/fx_exec/src/device_ops_interp_maps.rs` | yes (`NAN_EXACT_WRITTEN`) | yes |
| `warp_rel` | `crates/effects/fx_exec/src/device_ops_warp.rs` | no (the hardware NaN rule; NaN outputs rerun on the CPU) | yes |
| `make_mipmap` | `crates/effects/fx_exec/src/device_ops_ripmap.rs` | yes (`NAN_EXACT_COMPILED`) | yes |
| `dissolve` | `crates/effects/fx_exec/src/device_ops_pointwise.rs` | yes (`NAN_EXACT_COMPILED`) | yes |
| `element_of` | `ELEMENT_OF`, same file | yes (`NAN_EXACT_WRITTEN`) | yes |
| `monochrome` | same file | no | yes |
| `xy_to_polar`, `hsv_to_rgb` | `XY_TO_POLAR`, `HSV_TO_RGB`, `crates/effects/fx_exec/src/device_ops_retime_polar.rs` | yes (`NAN_EXACT_WRITTEN`) | no (refused Result answers only) |

No op has a `CPU_ONLY` entry. `optical_flow` on the device keeps the crates' own control code on the host: the level table, the copy and range scan of the first level, the range scan and row sums of each level, and the loop tests of the solve, each of which reads one word back from the device. The pyramid levels, the iterated solve, the smoothing passes and the final warp run as device kernels on planes that stay on the device. The reductions keep the CPU's order: the row sums, the range scans and the residual sum run as one work item that walks the rows in the crate's order (eight lane partial sums in the vector form), the forward splat and the scalar scan of `optical_flow_interp_maps` run as one work item each in raster order, and its zero count runs one work item per row and then one work item for the sum. The device placement takes the same `flow_host_phase` as the CPU and refuses an invalid one (`accepts_refuses_an_invalid_host_phase` in `device_flow_op.rs`). The compare drivers also run mutants of the kernel sources, each of which must be refused (`device_flow_op.rs`, `device_flow_fetch.rs` and the other device test files above).

A node runs on the CPU when its kernel declines the shape (`unsupported`), when its op failed the self-check (`not_allowlisted`), on `memory` or `opencl_error`, and for a NaN output of an op that is not NaN exact on that device (`nan_output`). MEASURED on PoCL only: every node runs on the device with the CPU's bytes and `fallback: none` on all 58 runs of both stages through `fx_run` (24 recorded renders and 34 parameter runs), 291 device nodes on Retime_Speed and 231 on Retime_Longer, the same at threads 1, 3 and 12; `device_retime` and `device_retime_polar` pass 2 and 6 tests (the `S_Retime` section of [Effects](../effects.md), [Rendering on a device](../guide.md#rendering-on-a-device)). Timing of one 1920x1080 frame ([Speed](../guide.md#speed), PoCL is an OpenCL runtime on the CPU and shows correctness, not GPU speed): `retime_speed` CPU 20.91 / 20.68 s, PoCL 3.85 / 3.93 s; `retime_longer` CPU 20.72 / 20.34 s, PoCL 3.95 / 4.08 s.

## Changing the code safely

- Gates that stay green: `python -I tools/fx_golden.py` (plain, special and threaded rows, on the CPU and with `SAPPHIRE_DEVICE=gpu SAPPHIRE_REQUIRE_DEVICE=1`), the crate tests above including the two crates outside the default members, the executor and stage tests, `python -I tools/test_effect_rules.py`, the device self-check, compare and mutation tests (one thread), the NaN tests CI runs on x86 and on the macOS arm64 runner, `python -I tools/check_docs.py` and `python -I tools/gen_docs.py --check`.
- A golden difference means the output bytes changed. The table holds this repository's own renders, so the repository alone cannot say whether the original agrees; only the recorded renders and the comparison harness can. `python -I tools/fx_golden.py --write` rewrites `tools/fx_golden.tsv` from the current build; it is used only after a change has been checked against the recorded renders, never as a check.
- Placement: a change to `placement.rs`, to the plane order of the flow op or to `flow_host_phase` moves the phase every row sum sees and can change the output at widths of 64 or more without changing any 50x7 row; the `64x32` golden rows and `placement_bit5.rs` are the in-repository guards. The device placement must stay equal to the CPU placement plane by plane.
- Kernel rules ([Adding an effect](../adding-an-effect.md)): no platform math library call in effect code (`tools/test_effect_rules.py`, exceptions in `tools/fx_math_allow.tsv`); a fresh NaN canonicalized to 0xffc00000 before a sign operation; two-NaN picks through `fx_common::nanop`; `mul_add` exactly where the original fuses. A CPU parity change to any op of the table above removes it from `ALLOWLIST` in `crates/effects/fx_exec/src/device_ops.rs` unless its device kernel changes in the same patch; a kernel change keeps its compare driver and mutants passing.
- Docs and data to update with a change: the `S_Retime` sections of [Effects](../effects.md) and [Driving the effect parameters](../parameters-guide.md), the refusal rows of [Command-line reference](../cli.md#refusal-labels), the stage rows and [Effects provider](../stages.md#effects-provider), `docs/data/effects_status.tsv` (then `python -I tools/gen_docs.py`), and this page.
